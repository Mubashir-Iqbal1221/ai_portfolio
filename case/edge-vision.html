Safety alerts on edge devices, and an agent to question them

A facility has many cameras and few people watching them. We delivered a system that watches camera feeds on an edge device, flags violence, falls and intrusions, and lets operators ask about any event in plain words, by voice or text. I also converted the vision pipeline to DeepStream and optimised it to run fully on the device.

At a glance

  • Client: a secure facility
  • Scope: first version delivered and deployed, with the vision pipeline moved from a cloud VM onto a Jetson
  • My role: built the operator agent over the event database, set up the Jetson, and converted the vision pipeline to DeepStream and optimised it for the device, end to end
  • Result: one pipeline runs 4 cameras at 13.7 fps each; app RAM down from 2.3 GiB to 0.57 GiB
  • Stack: NVIDIA Jetson, DeepStream, TensorRT, YOLOv8, Google ADK, Gemini, LiteLLM, MCP Toolbox, PostgreSQL, Tailscale, Docker

The problem

A fight or a fall needs a response within moments, but running a large model on every frame of every camera is too slow and too costly for a device on site. Once an event is flagged, operators also need answers fast, without scrubbing through footage or writing SQL.

What we built

  • A funnel from cheap checks to costly ones. Each camera is sampled down to a few frames per second. Quick checks catch camera tampering, frames with nobody in them stop at person detection, and pose and motion give each frame an anomaly score. Only high-scoring frames go to a vision-language model, so most frames never reach the costly step.
  • An agent operators can question. I built the agent operators use to ask questions such as how many falls happened at a site this week. It answers by text or voice, draws charts, and writes an incident report for each event.
  • Open questions, without open access. Operators ask questions nobody can list in advance, so a fixed set of predefined queries would not cover them, and the agent writes its own SQL. To keep that safe without relying on the prompt, I created a database user with only the access we chose to expose, and the agent's database toolbox connects through that user alone. Row-level security then limits every query to the user's own organisation and sites.
  • Sessions that pick up where they left off. Conversations are saved, and a voice session resumes from a cleaned, trimmed history, so old audio and tool output cannot confuse the model.
  • The device, connected. I configured the Jetson, connected its services, and set up secure network access to it with Tailscale.

The vision pipeline, in DeepStream on the device

The vision pipeline first ran as Python code with PyTorch on a cloud VM. I converted it to DeepStream, moved it onto a Jetson Orin Nano, and optimised it for that device.

  • Both models on the device, without PyTorch. I moved the pose model to a TensorRT engine and wrote its keypoint decoder. PyTorch is no longer in the running app, and the image is 2.4 GB smaller.
  • Matched to the original, not just faster. The first port found 174 of the 340 people the original model found. I traced it to black square padding and moved gray padding into the model file, which brought it to 325 of 340. For the detector, a rectangle input and one DeepStream setting for boxes at the frame edge gave a 100% match with Ultralytics.
  • One pipeline for up to four cameras. I replaced one pipeline per camera with one shared pipeline. Cameras join and leave while it runs. The first RTSP camera crashed it, a fault that file tests had hidden; I found the cause and fixed it.
  • Measured before keeping. I tested six ways to move work to the GPU, each behind a switch, with 1 and 4 cameras. I kept the three that saved CPU with the same detections: a smaller live picture, the tamper check on the GPU, and no drawing while nobody watches. Detection and events never stop.
  • Clips that last, on a disk that does not fill. Event clips are MP4 files on the device's NVMe, served with signed links. Clips older than 7 days are deleted, and the oldest go first when the disk is over 80% full.
  • A new Jetson in one command. Export scripts rebuild both models on any Jetson, and one setup script checks the device, builds everything and tests the install.
